# Repository audit, industry comparison and next steps (2026-11-10)

Scope: `main` at `0aeca14` (DOOM side project merged, `doom-done`). Method: reading of the specs, RTL, driver, FPGA
integration and the project logs; the Cheshire, `axi_vga` and `axi_llc` sources were read from their public
repositories to check the VGA analysis (file / line references below are to those repositories' `main`, not to the
pinned commit `6c6dd5e`: re-check the two LLC facts at the pinned commit before acting).

**Not done in this audit:** no simulation, lint or build was run (the audit machine had no Verilator / cocotb /
pybind11). The last recorded result stands: `make test` 101 / 101 on 2026-11-06 (docs/HANDOFF.md). Every item marked
*hypothesis* or *estimate* is unverified (CLAUDE.md rule 9).

Contents: 1 summary, 2 VGA flicker in the DOOM demo (cause and fix), 3 findings, 4 comparison with commercial 2D
GPUs, 5 answers (use everywhere? OpenVG? 3D GPU?), 6 proposed plan (the roadmap change is in docs/ROADMAP_V2.md §1.0b).

## 1. Summary

- The design itself is in good shape: spec-first, bit-exact golden model, self-checking tests, mutation testing, a
  generated register map, textbook CDC, a real error / soft-reset model, an address window on the memory port. No new
  functional RTL bug was found by reading.
- The weak point is **the distance between "passes in simulation" and "works on the board"**. Three board bugs are
  open (Q-FPGA-9 / 10 / 11), the features of v1.3–v1.7 never ran correctly on hardware (the DOOM bitstream is
  FEATURES = 0), and the async build never ran on the board at all. Verification uses one 2-state RTL simulator and no
  netlist simulation; that is the gap Q-FPGA-10 fell through.
- The VGA flicker has a concrete cause in the SoC memory path, not in the GPU (§2). It can be confirmed with a
  software-only test and fixed in three small steps.
- Against commercial 2D vector GPUs the feature list is already competitive. What is missing for "industry standard"
  is mostly outside the pixel pipeline: a display controller, silicon numbers (the 600 MHz target has no evidence
  yet), low power and DFT, an operating-system driver, thread safety, packaging, a licence, CI (§3, §4).
- It is a 2D / 2.5D GPU. It can be a good UI and 2D-game GPU; it cannot run 3D games or anything that needs
  OpenGL ES / Vulkan (§5).

## 2. The VGA flicker in the DOOM demo (Q-FPGA-11)

### 2.1 What is established

Numbers for 640 × 480 RGB565 at a 25 MHz pixel clock (SoC clock 50 MHz):

| Quantity | Value |
|---|---|
| Frame | 614 400 B = 76 800 beats of 64 bit = 9 600 LLC lines of 64 B |
| Scan-out demand | 1 beat per 8 SoC cycles inside a line, 1 per 10.9 averaged over the frame |
| Buffer (256 beats) | 1 024 pixels = 1.6 lines = about 41 µs = about 2 050 SoC cycles |
| DOOM present by G2D | reads 64 KB (320 × 200 INDEX_8), writes 614 KB, every game frame |
| LLC | 8 ways × 256 sets × 8 blocks × 8 B = 128 KB, write-back |

Facts from the sources:

1. **The frame buffer goes through the last-level cache.** Cheshire's cached region is all of DRAM
   (`LlcOutRegionStart/End` = `0x8000_0000 .. 0x1_0000_0000`, cheshire_pkg.sv). `axi_llc_config` sends cached-region
   requests to the bypass only when every way is flushed (`axi_addr_map[1].idx[0] = &conf_regs_i.flushed`), which is
   the boot-ROM state (all ways scratchpad). `doom_chs.c` `llc_to_cache()` (DOOM_LLC_CACHE = 1) switches the ways to
   cache before the game starts. From then on the scan-out reads, the G2D source reads and the G2D frame-buffer
   writes all run through a 128 KB cache in front of a 614 KB frame buffer: nearly every line is a miss, and a miss
   is an eviction write of a dirty line plus a refill read before the request is served. The v1.2 VGA test and the
   board scene tests ran with the LLC in bypass, which is why the problem first appeared with DOOM.
2. **The scan-out reads are single beats.** `axi_vga` puts an `axi_burst_splitter` behind its fetcher, so every
   8-byte beat is its own AR. Cheshire's crossbar arbitrates per transaction (round robin). G2D issues 32-beat
   bursts with up to 16 reads and 8 writes outstanding (`MAX_BURST_BYTES = 256`, `RD_OUTSTANDING = 16`,
   `WR_OUTSTANDING = 8`). One scan-out beat competes with one 32-beat burst.
3. **An underrun damages the rest of the frame.** `axi_vga_timing_fsm` has `ready_o = visible & fsm_en` and outputs
   black when `valid_i` is low: a pixel is consumed on every visible clock whether one is there or not. The fork's
   re-sync repairs the alignment only at the next vertical sync.

*Estimate* (not measured): with a miss costing 40–70 SoC cycles (eviction + refill through the MIG's CDC), scan-out
alone needs 9 600 misses per 840 000-cycle frame, i.e. roughly half of the LLC's miss capacity while nothing else
runs. During a present the G2D write misses share the same single eviction / refill pipeline. If the two alternate
line by line, the scan-out gets a line every 80–140 cycles and needs one every 69–87: it falls behind for the whole
present (milliseconds), far longer than the 41 µs buffer. A bigger buffer cannot fix a throughput deficit; that
matches the board history (16 → 256 beats: no change; prefetch: better, not gone) and "fewer glitches with a smaller
DOOM window" (less CPU write-back traffic through the same pipeline).

### 2.2 Fix, in order

| Step | Change | Needs | Expected |
|---|---|---|---|
| 0 Measure | Counters in the fork: visible pixels shown without data, minimum buffer level per frame, worst AR-to-R latency; read them through spare `chs_ps2` registers and print them in DOOM's statistics line | new bitstream (can ride with step 2) | numbers instead of the estimate above |
| 1 Confirm (software only) | SD image built with `DOOM_LLC_CACHE=0` (LLC stays in bypass), same bitstream | 10 minutes, no bitstream | if the blinks disappear, the LLC is the cause (fps will drop: the CPU loses its L2) |
| 2 Real bursts | In `fpga/cheshire/axi_vga_g2d/axi_vga.sv` remove the burst splitter, the credit counter and the `stream_join`: the fetcher's AR goes out as one 64-beat burst. The fork's `committed_q` accounting already guarantees buffer room for every accepted burst, which was the splitter's only job. Replace the flop-based `stream_fifo` by a block-RAM FIFO and raise the depth to 1 024 beats (*to check*: `stream_fifo` is register-based, so "BRAM is free" in Q-FPGA-11 does not hold for the current module) | bench `test_axi_vga.py` (add: AR length ≥ 32 seen, R back-pressure), bitstream | scan-out gets 64 beats per arbitration turn instead of 1 |
| 3 Frame buffer out of the cache | Add to `cheshire-g2d.patch`: a separate cached-region end for `i_llc` (`cached_end_addr_i`), e.g. cache `0x8000_0000 .. 0xB000_0000` (program, heap, WAD) and place the GPU pool (`G2D_POOL_ADDR`) above it. Uncached addresses decode to the LLC bypass. The CPU stays coherent: it reaches the pool through the same bypass and its own D-cache is flushed by `fence` as today | SoC sim (the existing DOOM / VGA checks), bitstream | no eviction / refill for scan-out and G2D traffic; DDR sees plain bursts; the CPU keeps its cache for itself |
| 4 Harmless underruns | Line-based fetch: at every horizontal sync start the line at `START + y × stride` into a line buffer; if the line is not complete when it is needed, show the previous line again and count it | fork RTL + bench | a late line is invisible instead of a broken half frame |
| 5 Fair share | A memory-port throttle in G2D (CSR: maximum outstanding bursts and a minimum gap), default off; FPGA DOOM build sets it. Already in the roadmap as "QoS / bandwidth cap" | regs.yaml, RTL, test | bounded latency for every other manager |
| 6 Software | Present only when DOOM's screen changed; measure fps with the single-buffer wait removed | sw | fewer bytes per second |

Steps 1–3 should be enough for a clean picture; step 4 makes the scan-out robust for every later demo. The clean
long-term answer is an own display controller (§6, v1.9): it scans DOOM's 320 × 200 indexed screen directly (CLUT and
2 × scaler in the scan-out), so the present costs no GPU bytes at all.

Checked and found correct in the fork: the flip is tear-free (START_ADDR is reloaded while the fetcher is disabled in
RS_DRAIN, inside the vertical sync), the triple-buffer accounting in `doom_g2d.c` is safe, the prefetch across the end
of a frame only wastes up to one buffer of reads.

|---|---|---|---|
| C-1 | H | The driver is not thread-safe and has one global context (`g_drv`); no locking hooks in the HAL | HAL lock / unlock hooks (no-ops on bare metal) around every public entry; needed for any RTOS or Linux use |

## 4. Comparison with commercial 2D vector GPUs

Reference class: licensable 2D / vector GPU cores for microcontrollers and wearables and their display companions.
The comparison is by publicly described capability classes; no vendor numbers are quoted because none were verified
here.

| Area | This project | Typical commercial core | Gap |
|---|---|---|---|
| Vector fill, anti-aliasing | Paths with 16 samples per pixel, non-zero / even-odd | same class | none |
| Path processing | CPU transform, flatten, stroke; hardware edge lists | path data consumed by the hardware or a tessellation unit | B-5 |
| Paint | solid, linear and radial gradients, image pattern with wrap modes | same | none |
| Blending | Porter-Duff, LVGL, OpenVG and SVG2 families, blend function | Porter-Duff, some OpenVG | ahead |
| Images | affine and perspective, point / bilinear / 3 × 3 Gaussian, colour key, CLUT, YUV with conversion, colour matrix, gamma, dither | same, plus mip-maps or prefiltering on some | B-6 |
| Formats | 32 / 24 / 16 / 8 bit, sub-byte alpha, indexed, YUV | same, plus vendor compressed and tiled formats | compressed frame buffers / textures (own open format possible) |
| Masks, scissor | A8 mask layers, multi-rectangle scissor | same | none |
| Display output | none (uses Cheshire's `axi_vga`) | companion display controller: layers, alpha, CLUT, cursor, underrun handling | **missing** |
| Performance | 1 px/clk, 50 MHz on a Kintex-7 | hundreds of MHz in silicon | B-1, unproven |
| Power, DFT, memories | none | clock gating, power-down, scan, BIST wrappers | B-2..B-4 |
| Bus | AXI4 master, AXI4-Lite slave, CDC option | AHB / AXI / APB variants | planned adapters |

## 5. Answers

### 5.1 Can this GPU be used everywhere, for example for games?

It fits where commercial 2D vector GPUs are used: user interfaces on microcontroller- and small-Linux-class systems
(LVGL today), instrument clusters, wearables, and 2D games (sprites, tiles, scaling and rotation, emulators, or DOOM
with the CPU rendering and the GPU scaling and presenting, as demonstrated).

It does not fit:

- 3D games and anything written for OpenGL, OpenGL ES, Vulkan or Direct3D: there are no triangles with depth
  buffering, no perspective-correct attribute interpolation, no shaders;
- desktop environments, browsers and UI toolkits that require OpenGL ES 2 or newer;
- any product today: no silicon data, open board bugs, no operating-system driver, no licence, and the project's own
  rule is non-commercial use.

"Usable" in the realistic sense means: a board-proven FPGA IP with a display controller, an RTOS and a Linux driver,
packaging and a licence. That is the plan in §6.

### 5.2 Does it have to be OpenVG compatible? Is that easy?

Not required, but reasonable, and mostly software.

- The hardware already follows OpenVG 1.1 semantics in many places (rendering.md cites it for arcs, dashes, radial
  gradients, stencil image mode, mask operations, the OpenVG blend family, sRGB / linear and premultiplied formats).
  OpenVG's object model (paths, paints, images, masks, four matrices, scissor rectangles, colour transform) maps onto
  what the driver has.
- Work: an API layer of about 90 `vg*` functions plus the VGU utilities over the internal driver (not over the
  `vg_lite_*` calls, so both APIs share state handling): handle and context management, parameter getters / setters,
  error codes, path queries (length, point along path, bounds: geometry library), fonts and glyph drawing (on paths
  and images), pixel read / write / copy (blits). Software fallbacks for what the hardware lacks: general
  convolution, separable convolution, lookup-table image filters, large Gaussian blur.
- The hard parts are not the drawing: an EGL layer for contexts and surfaces (a minimal one on bare metal / RTOS is
  small, a real one on Linux is not), and conformance. The Khronos conformance tests and the right to call a product
  "OpenVG" are for Khronos adopters; the public OpenVG 1.1 reference implementation can serve as an image reference
  with a tolerance (*to verify*: its licence terms before importing anything).
- Size: medium, a few months part-time, no RTL change needed for a first version.
- Value: OpenVG has not been revised since version 1.1 and new adoption is low. It opens Qt Quick's OpenVG backend
  (*to verify* for the Qt version targeted) and legacy automotive / embedded code. For new embedded projects the
  VGLite API (LVGL, NuttX) reaches more users, and for Linux-class software OpenGL ES 2 is the entry ticket, which
  only a 3D GPU provides.

Recommendation: do it as a software-only version after v2.0, not before the board and driver work.

### 5.3 A 3D GPU: on top of this one or from zero?

Neither exactly: a **new pipeline in a new IP that reuses this project's platform**.

- Do not extend `g2d_pix` / `g2d_raster`: a scanline edge-list rasterizer with coverage accumulation is the right
  shape for vector paths and the wrong one for triangles with depth, attribute interpolation and (later) shading.
- Do not start from zero either. Directly reusable: the AXI master with its read clients and write combiner, the
  command processor (kick queue, fence, error and soft-reset model), the register generator flow, the CDC wrappers,
  pixel-format unpack / pack, the blend unit, the texel cache and bilinear sampler, the perspective divider, the
  cocotb environment and AXI memory models, the golden-model method, the HAL, the Cheshire integration and the
  display path. New: triangle setup, a barycentric (edge-function) rasterizer, depth / stencil buffer, perspective-
  correct interpolation, mip-mapped texturing, a 3D golden model.
- The software is the larger half. Two realistic levels:
  1. **Fixed function (OpenGL ES 1.1 / early-PC-accelerator class):** vertex transform on the CPU, hardware
     rasterization with depth test, one or two textures, fog, alpha test. An own small GL library is feasible for one
     person, and it runs the 1996–2000 game generation (Quake-class engines).
  2. **Programmable (OpenGL ES 2 and later):** shader processors plus a shader compiler; in practice a Mesa driver.
     That is a multi-year effort and should only follow level 1.
- Sensible structure: a shared repository of common blocks (bus, command processor, formats, blend, sampler, tests)
  used by `g2d` and a sibling `g3d`; both render into the same frame buffers and can sit behind one display
  controller. Start it after G2D v2.0: the board-proof and netlist-simulation lessons should exist first.

## 6. Proposed plan

Detailed table: docs/ROADMAP_V2.md §1.0b (proposal, not approved). In short:

1. **v1.8 Board-proven** (unchanged goal, more precise content): VGA fix steps 0–4 of §2.2, Q-FPGA-10 with the
   netlist-simulation stage and synthesizable collision / signature debug (A-1, A-2), Q-FPGA-9, full-feature and async
   board regression, CI, README and licence decision.
2. **v1.9 Display controller and memory QoS** (new): own `g2d_dc` (timing generator, line-buffered fetch with underrun
   repeat and counters, vsync interrupt and flip register, RGB565 / ARGB8888 / indexed + CLUT, integer scaler, two
   layers with alpha), G2D memory throttle, DOOM and LVGL demos on it.
3. **v1.10 Bus adapters and packaging** (the old v1.9), plus SDC template and memory-macro layer.
4. **v2.0 Drivers and closure**: thread-safe driver, interrupt-driven wait, one RTOS HAL, Linux driver as planned,
   ASIC numbers from the open flow, every open question closed.
5. **After v2.0**, each its own decision: OpenVG 1.1 API layer (software); ASIC hardening (pipelining to the measured
   target, clock gating, DFT, BIST wrappers); hardware path front end; mip-maps and an open compressed format; G3D.

Decisions needed (one batch): docs/ROADMAP_V2.md §1.0b.
